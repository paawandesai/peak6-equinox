## M3-01: Router eligibility — staleness and skew

**Context:** M1 router v0 walks a book without checking quote freshness or time skew between venues. NFR-09 requires quotes older than 120 s to be ineligible on live data, with skew above 5 s warning and above 30 s excluding (configurable). AB-10 demands logged timestamps and exclusion reasons in the trace.

**Satisfies:** FR-15 (staleness/skew), NFR-09 (partial), AB-10 (partial), US-05

**Acceptance criteria**
- [ ] `internal/route/eligibility.go` implements quote-local checks: `IsEligible(q canonical.Quote, now time.Time, cfg EligibilityConfig) (bool, []string)` for staleness, missing book, and depth. NEW type `EligibilityConfig` derives from existing `config.Config`: reuse `config.StaleAfter`, `SkewWarn`, `SkewMax` (time.Duration fields already exist); add `MinBookDepth decimal.Decimal` field if needed.
- [ ] Staleness: `now - q.FetchedAt > cfg.StaleAfter` excludes with `ReasonStale` (add constant = `"stale"`) and detail `"fetched N s ago"` (Reason + Detail pattern, matching ReasonNoBook/InsufficientDepth). Use existing `config.StaleAfter` time.Duration field. A missing or zero `FetchedAt` is ineligible.
- [ ] Missing book (`q.Quality` flag `no_book` or both `YesAsks` and `YesBids` empty) excludes with `ReasonNoBook` (`"no_book"`) (reuse the existing reason constant from route.go).
- [ ] Insufficient depth: if the best N contracts available (walk the book) is less than `MinBookDepth`, exclude with `ReasonInsufficientDepth` (`"insufficient_depth"`) and detail `"X contracts available"` (reuse the existing reason constant from route.go).
- [ ] Skew (two-quote comparison): separate function `Skew(q1, q2 canonical.Quote, cfg EligibilityConfig) (excludeOlder bool, warnings []string)` where config includes `cfg.SkewWarn`, `cfg.SkewMax` (time.Duration). When `abs(q1.FetchedAt - q2.FetchedAt) > cfg.SkewMax`, returns `(true, [])` to exclude the older quote with `ReasonSkew` (add constant = `"skew"`) and detail `"X s behind"` (Reason + Detail pattern). Skew between `cfg.SkewWarn` and `cfg.SkewMax` returns `(false, ["skew_warning: X s behind"])` for `Decision.Warnings`. Use existing `config.SkewWarn`/`SkewMax` time.Duration fields.
- [ ] Relationship confidence filtering (MIN_ROUTE_CONFIDENCE=0.9) is applied when selecting routing partners in `internal/route/route.go`, not inside `IsEligible`. Relationships below the threshold are excluded with `ReasonLowConfidence` (`"low_confidence"`) and detail `"confidence %s is below the %s floor"`, reusing today's `partnerExclusion` constant and format.
- [ ] `internal/route/route.go` applies eligibility per leg; the decision's `Explanation` names each excluded venue and why, and warnings appear in `Decision.Warnings`.
- [ ] Table-driven tests: stale, skewed, shallow, missing-book cases, and a happy-path eligible quote.
- [ ] Property test: skew is symmetric (if A is skewed against B by X, then B is skewed against A by X, within ordering ties).
- [ ] Default config values are already in `internal/config/config.go` and `docs/environment.md`: `STALE_AFTER_SECONDS=120`, `SKEW_WARN_SECONDS=5`, `SKEW_MAX_SECONDS=30`, `MIN_ROUTE_CONFIDENCE=0.9`. NEW env var `MIN_BOOK_DEPTH` if needed (default 1 contract, add to config/environment.md).

**Verification:** `go test ./internal/route/... -run 'Eligib|Stale|Skew' -v && make cover`

**Dependencies:** none (M2 complete)
**Files likely touched:** `internal/route/eligibility.go` (NEW), `internal/route/eligibility_test.go` (NEW), `internal/route/route.go`, `internal/config/config.go` (config), `docs/environment.md` (env defaults), `docs/decisions.md`, `docs/log.md`

## M3-02: Basis penalty in routing cost

**Context:** FR-11 basis-risk scoring exists (M2-04); FR-12 says "all-in cost = VWAP + fee + basis penalty." The router must apply the basis-risk score as a cost penalty so a higher-risk equivalent is chosen only when the price advantage exceeds the risk.

**Satisfies:** FR-11 (in routing), FR-12 (basis term), US-03

**Acceptance criteria**
- [ ] `internal/route/route.go` computes `allInCost = vwap + feePerContract + basisPenalty`. Basis penalty is `relationship.BasisRisk.Score * BASIS_PENALTY_MULTIPLIER` (cents per contract per risk point; configurable, default 0.01 = 1 cent per 1.0 risk point). NEW env var `BASIS_PENALTY_MULTIPLIER` (add to config.Config, default 0.01, document in environment.md). Extend route.Config to include basis multiplier and fee calculator.
- [ ] The decision's cost breakdown per leg shows `vwap`, `fee`, `basis_penalty` and `total` separately, with the basis-risk score and the multiplier documented in the trace.
- [ ] When two venues have the same all-in cost (within 0.0001 tolerance), ties go to the deeper book (most contracts available at or better than the touch), then to the lower basis score, then to the lexicographically first venue name (deterministic).
- [ ] Complement routes (M3-04) also apply the basis penalty from the complement relationship.
- [ ] Remove the hard-coded `"basis-risk penalty is not applied in v0"` warning in route.go `warnings()` (line 313) once the penalty is applied in allInCost calculation.
- [ ] Update `internal/route/explain.go` (line 39): change "No basis-risk penalty is applied in v0" to reflect that the penalty is now applied in the all-in cost calculation.
- [ ] Table-driven tests: basis flips a decision (venue A cheaper VWAP but higher basis → venue B wins), ties resolved by depth, basis penalty 0 when `BasisRisk.Score` is 0.
- [ ] Property test: monotonicity (increasing basis score never decreases all-in cost).
- [ ] NEW env var `BASIS_PENALTY_MULTIPLIER` wired from config (default 0.01), add to `internal/config/config.go` and `docs/environment.md`.

**Verification:** `go test ./internal/route/... -run 'Basis|Cost|Tie' -v && make cover`

**Dependencies:** M3-01 (eligibility shape in route.go)
**Files likely touched:** `internal/route/route.go`, `internal/route/explain.go` (update "No basis-risk penalty" sentence), `internal/route/route_test.go`, `internal/config/config.go`, `docs/environment.md`, `docs/decisions.md`, `docs/log.md`

## M3-03: Greedy sweep / split across venues

**Context:** FR-13 requires a greedy multi-venue sweep when one book can't fill the order. The router walks each eligible book from best to worst, filling as much as possible per venue, then combines legs in a decision.

**Satisfies:** FR-13, US-03

**Acceptance criteria**
- [ ] `internal/route/sweep.go` implements `Sweep(order canonical.Order, candidates []canonical.Candidate, cfg Config) []canonical.Leg`. Use existing `canonical.Candidate` type (Instrument + Quote + Relationship); internal/route already wraps it in unexported `candidate` with route string. Ranking by all-in cost needs `Config` for fees and `BASIS_PENALTY_MULTIPLIER`; pass config in. Each `Leg` uses the existing canonical.Leg fields: `InstrumentID`, `Venue`, `Side`, `Outcome`, `Quantity`, `VWAP`, `FeePerContract`, `BasisPenaltyPerContract`, `AllInPerContract`, `Route`.
- [ ] Greedy algorithm: rank candidates by all-in cost per contract (ascending), walk each book from best to worst price level, consume levels until the remaining order size is 0 or the book is exhausted, then move to the next venue. Stop when filled or all venues exhausted.
- [ ] **IOC (Immediate or Cancel):** if the order can be partially filled, `Chosen` contains the fill, and `Alternatives` includes the partial option with `Note` prefixed by `NotePartial` (e.g., `"partial fill: 80 of 100 contracts"`). **FOK (Fill or Kill):** partial fills are rejected; a partial option must NOT appear in `Alternatives`. FOK with insufficient liquidity has empty `Chosen` and the exclusion reason in `Exclusions`.
- [ ] A completely unfilled order (all venues ineligible or shallow) has empty `Chosen` with per-candidate reasons in `Exclusions` (e.g., `ReasonInsufficientDepth`, eligibility reasons). Do not overload `ReasonNotRoutable` (`"not_routable"`) for all-ineligible — that constant means the relationship type is never routed (today's `partnerExclusion`).
- [ ] The decision's `Explanation` lists legs in cost order and shows the total filled, total cost, average all-in price, and any shortfall. Book-walk details (levels consumed) can be logged or included in the explanation text, but do not invent new Leg or Decision fields.
- [ ] Table-driven tests: single-venue fill, two-venue split (venue A fills 60%, venue B fills 40%), IOC partial fill (order larger than books, partial in Alternatives with NotePartial), FOK partial rejected (no partial in Alternatives, empty Chosen), all ineligible (empty Chosen, per-candidate reasons like ReasonInsufficientDepth in Exclusions).
- [ ] Property test: greedy never leaves a cheaper unfilled contract when a more expensive one was filled (within the same venue, the book walk is monotonic).
- [ ] Integration with M3-01 eligibility: ineligible candidates are excluded before sweep.

**Verification:** `go test ./internal/route/... -run 'Sweep|Split|Partial' -v && make cover`

**Dependencies:** M3-02 (cost calculation)
**Files likely touched:** `internal/route/sweep.go`, `internal/route/sweep_test.go`, `internal/route/route.go` (wire Sweep), `docs/decisions.md`, `docs/log.md`

## M3-04: Complement routing

**Context:** FR-14 / US-04: when A and B are complements, buying YES on A is economically equivalent to buying NO on B, so the router should compare both. Domain.md § Business rules: "Complement route: buying YES on A is equivalent to buying NO on B when A and B are complements, so the cost is B's NO ask."

**Satisfies:** FR-14, US-04

**Acceptance criteria**
- [ ] `internal/route/route.go` (or `complement.go`) extends `Route` to consider complement relationships in addition to `equivalent` and `equivalent_given_facts`. For each complement pair where the relationship confidence is above `MIN_ROUTE_CONFIDENCE`, add a candidate with the opposite side (YES ↔ NO).
- [ ] The complement candidate's cost is computed as `oppositeVWAP + fee + basisPenalty`, where `oppositeVWAP` walks the NO book when the original order is YES (and vice versa).
- [ ] The decision trace clearly marks complement legs using the existing `Leg.Route` field: set `Route = "complement"` (vs `"direct"` for non-complement). The leg's `Side` and `Outcome` reflect the actual trade (e.g., NO on the complement instrument).
- [ ] Greedy sweep (M3-03) includes complement candidates ranked by all-in cost alongside direct equivalents, so a cheaper complement route can win.
- [ ] The explanation says: "Chose NO on [B] (complement of [A]) at venue X because the all-in cost (VWAP + fee + basis) was $Y per contract, vs $Z for YES on [A] at venue W."
- [ ] Table-driven tests: complement is cheaper than direct (complement wins), direct is cheaper (direct wins), a mix of equivalent and complement candidates, complement with a partial fill.
- [ ] Property test: flipping the original order's side and running the router on the complement pair should produce the inverse route (within cost tolerance).
- [ ] `internal/route/imports_test.go` still passes (route may import canonical, fees, decimal, stdlib only).

**Verification:** `go test ./internal/route/... -run 'Complement|Opposite' -v && make cover`
